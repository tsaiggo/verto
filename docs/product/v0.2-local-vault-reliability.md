# Verto v0.2 — Local Vault Reliability

## Product outcome

Verto should be safe to use as the primary reader and editor for a real
Markdown or MDX vault. The selected folder remains the source of truth, while
OneDrive, Dropbox, iCloud Drive, Syncthing, or another filesystem provider may
sync that folder between devices. Verto does not add a cloud account or a
second remote copy.

## Delivery order

### 1. Restore the canonical reading workbench

- Wide screens use `Outline → document → Agent`.
- The document remains the primary column.
- The Outline progressively folds into the document below the wide breakpoint.
- The Agent remains available without forcing horizontal overflow.

### 2. Make document writes conflict-safe

Every editable document session records the content revision that was read
from disk. A normal save succeeds only when that revision still matches the
current file.

If another editor or sync provider changed the file, Verto must not overwrite
it silently. The user can:

- reload the disk version,
- explicitly replace the disk version, or
- keep the local draft while deciding how to merge it.

The native writer does not rely on a check followed by an unconditional
rename. It atomically captures the file actually displaced at replacement
time, compares that captured revision, and restores it if a provider wrote in
the comparison window. Content and file metadata are both checked, so a
provider changing a file to read-only is also treated as a conflict. On
Windows, an active external writer handle prevents replacement. Displaced
versions implicated in a conflict or ambiguous restoration are retained in a
marked `.verto-recovery/` directory; verified normal Windows saves do not
accumulate backups. Verto recognizes only its marker and recovery artifact
format, treats any unexpected entry as an obstruction, and never discovers or
deletes files by a loose filename prefix. The directory is fail-closed at 64
artifacts or 512 MiB, so a full recovery budget stops the next exchange before
the canonical file changes. Restoration follows newer atomic provider
publications for a bounded number of attempts and retains every observed
version before another exchange, so a conflict cannot silently roll the
canonical pathname back to an older provider version.

On POSIX platforms, the operating system does not offer the same mandatory
writer exclusion for an arbitrary process that already holds the old inode.
Verto therefore retains successfully displaced user-document inodes in that
bounded recovery directory until the user reviews them. Creating a missing
file uses a no-clobber operation. Only a flushed and re-verified canonical file
is reported as saved.

### 3. Observe external filesystem changes

The desktop shell watches the active authorized vault recursively and emits a
small, serializable event for relevant Markdown and MDX changes.

```ts
interface VaultChangeBatch {
  schemaVersion: 1;
  root: string;
  generation: number;
  sequence: number;
  rescan: boolean;
  changes: Array<
    | { kind: "upsert"; entry: VaultEntry }
    | { kind: "remove"; id: string; path: string[] }
    | { kind: "rename"; fromId: string; fromPath: string[]; entry: VaultEntry }
  >;
  portableStateRescan: boolean;
  portableStateNames: string[];
}
```

The watcher:

- keeps `.verto` out of the content index while separately invalidating direct
  portable state JSON files; conflict, recovery, and staging artifacts remain
  internal,
- ignores other hidden paths, temporary files, and irrelevant write echoes,
- streams content fingerprints within a 32 MiB per-file limit and removes an
  indexed entry if that file grows beyond the limit,
- coalesces bursts before they reach React,
- preserves both paths for a rename when the platform reports them,
- falls back to `rescan` when an event cannot be classified safely, and
- turns skipped sequences into an authoritative content and portable-state
  rescan,
- reports an unavailable watcher, and
- falls back to wake-driven plus ten-second polling refreshes for both content
  and portable state rather than presenting stale data as current.

### 4. Refresh the index incrementally

A filesystem event invalidates only affected documents. Unchanged entries are
reused using their path, modification time, size, and known content revision.
Search, tags, Library sections, and the Vault tree consume the same refreshed
index.

The indexer must discard stale async results when a newer filesystem revision
starts and remain responsive for large synced vaults.

Full listings and direct document opens use the same 32 MiB content limit.
Oversized Markdown/MDX files are omitted from the Library, and a direct open
returns an explicit size-limit error. A file that changes size or modification
time while it is being read is retried through the normal watcher/rescan path
rather than publishing a partial snapshot. Windows excludes in-place writers
while reading; POSIX verifies a second streamed fingerprint from the same inode
so same-length changes do not publish a mixed snapshot.

### 5. Protect portable Verto state

Files below `.verto/` remain portable, but an automatic mirror must not
silently replace a state file changed by another device. State writes use the
same expected-revision rule as documents. On conflict, the latest local value
stays in the recovery journal and a recoverable conflict copy or backup is
created before any explicit replacement.

The production Windows build additionally excludes active external writer
handles against both the pre-exchange file and the newly published canonical
file until durable verification completes. On macOS and Linux, portable state
coordination covers Verto writers and sync providers that publish changes
atomically by pathname. POSIX does not provide mandatory exclusion for an
unrelated process that keeps an old inode open and writes it later, so that
path is explicitly best-effort rather than part of the strict guarantee.

A detected revision conflict is still fail-visible and preserves the local
payload in the journal and a marked conflict directory. Sidecars use
hash-encoded state and writer identities, retain at most five copies per
state/writer pair, and stop fail-closed at 64 files or 512 MiB across the
vault. Retention or capacity failures never create an additional copy; the
journal remains the authoritative unsaved payload. A known local staging file
is discarded after a pre-exchange failure rather than being duplicated
without bound; data that might be the only external version remains
fail-visible and recoverable.

This applies to:

- annotations,
- bookmarks,
- collections,
- reading state,
- summaries, and
- Agent threads.

### 6. Prove the production desktop path

The release gate uses a production bundle, not only the Next.js development
server:

1. build the Windows installer,
2. exercise a release binary with a smoke-only application identity locally,
3. install the production-identity MSI only in a clean CI user context,
4. launch the exact installed executable,
5. connect a temporary vault,
6. open, edit, and save a document,
7. restart and verify document plus portable state,
8. verify watcher create/modify/rename/delete behavior,
9. verify an external edit produces a conflict rather than data loss, and
10. verify an external portable-state replacement updates the open app without
    a restart, and
11. uninstall the exact MSI product code cleanly.

## Acceptance criteria

- Wide desktop Reader geometry is `Outline → document → Agent`.
- An external edit made after a document opens is never overwritten by a
  normal save.
- Create, modify, rename, and delete events appear without restarting Verto.
- A filesystem burst performs bounded reads instead of rebuilding every
  document body.
- Portable state survives restart and has a recoverable path when another
  device changes it; an external state replacement also refreshes the open
  desktop session.
- The platform-specific save guarantee is stated accurately: strict active
  writer exclusion on Windows, retained document recovery plus bounded
  backpressure on POSIX, and cooperative pathname coordination for POSIX
  portable state.
- Production browser E2E, the isolated release-binary smoke test, and the
  clean-CI Windows installer smoke test pass.
- Formatting, lint, type checking, unit tests, browser tests, Rust tests, and
  the production build pass before the pull request is ready.

## Non-goals

- A Verto-hosted sync service.
- Collaborative editing.
- Automatically resolving two divergent document bodies.
- Treating OneDrive or another provider as an API-owned database.
